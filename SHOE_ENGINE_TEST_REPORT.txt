AI RUNNING COACH — SHOE ENGINE CORRECTIVE RELEASE
Release: v14.0.8 · build 40008

ROOT CAUSE FOUND
The live planner still had an inventory-count purchase trigger:
    while(active.length < 2) -> create a new training pair

That contradicted the intended minimal-purchase strategy. It could create future shoes simply to restore a
two-pair inventory, even when the remaining physical pair(s) could still cover the programme. Later pruning
could not reliably undo the bad upstream purchase decision.

A second architectural issue tied session comparison to the forecast lifecycle pair list. An owned shoe that
the forecast was not currently using could therefore disappear from AVAILABLE SHOES even though the runner
still physically owned it and it was serviceable.

CORRECTIONS
1. OWNED PHYSICAL PAIRS ARE AUTHORITATIVE FOR SESSION AVAILABILITY
- Every state.shoes physical pair with status != retired is evaluated for every session.
- A forecast planner may choose not to assign a shoe, but that no longer makes the owned pair disappear.
- Future pairs appear only on/after their authoritative purchase / first-use date.
- Pair identity is physical-pair ID, not model family.

2. PURCHASES ARE NEED-DRIVEN ONLY
- The engine no longer purchases merely because fewer than two pairs are active.
- Existing owned/future physical pairs are evaluated first.
- A new ordinary pair is created only when no existing serviceable pair can cover the chronological session.
- An already-created future training pair is reused before another future training purchase can be created.
- Race Day selection prefers an owned or already-required race-capable training pair when suitability is close.

3. 25% WEEKLY RULE RETAINED
- The whole-session constrained weekly allocator remains active.
- It seeks >=25% of weekly running mileage for every genuinely available ordinary physical pair whenever
  feasible without splitting sessions or violating lifecycle/manual/suitability constraints.

4. DAILY PLAN SHOE UI REBUILT
- Collapsed daily cards show only shoe name + score.
- Expanded shoe section is a single full-width mobile column.
- AVAILABLE SHOES lists every genuinely available physical pair and its score.
- Compare shoe scores remains a full-width drill-down.
- Shoe model text uses normal word wrapping; it cannot collapse into one-character columns.

5. GRAPH
- Existing equal-mileage point suppression remains active.
- Purchases shown on the graph now come from the need-driven lifecycle rather than inventory-count maintenance.

REGRESSION LOCK
The app.js diff from v14.0.7 is restricted to version/cache metadata and Shoes-related ranking,
purchase/lifecycle and Plan shoe presentation functions. No training-plan generation, prediction,
pathway, recovery, HRV, injury progression, FIT/CSV import or execution-scoring engine was modified.

LIMITATION
The browser's private localStorage is not available in this execution environment. The fix therefore makes
owned state.shoes inventory authoritative at runtime, so the two physical pairs stored in the user's browser
are evaluated directly when the deployed build loads.
